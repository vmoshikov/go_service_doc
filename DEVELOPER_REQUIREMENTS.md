# Требования для разработчиков: CHANGELOG и комментарии в документации

Краткие правила для корректного попадания изменений в CHANGELOG.md и отображения описаний в генерируемой документации.

---

## 1. Именование веток и коммитов для CHANGELOG.md

- **Что попадает в CHANGELOG**: только **merge-коммиты** в диапазоне между тегами (или с указанного ref). Один merge = один пункт в CHANGELOG.

- **Имя ветки** должно:
  - Содержать **ключ задачи** в формате `KEY-NNN` (например `ABC-123`, `JIRA-456`), чтобы в CHANGELOG подставлялась ссылка на трекер (если настроен `task_tracker_url`).
  - Начинаться с **префикса категории**, иначе пункт попадёт в «Изменено». Рекомендуемые префиксы:
    - `feature/`, `feat/` → **Добавлено**
    - `fix/`, `bugfix/`, `hotfix/` → **Исправлено**
    - `refactor/`, `release/` → **Изменено**
    - `remove/`, `revert/` → **Удалено**

- **Примеры имён веток**: `feature/ABC-123-add-user-api`, `fix/ABC-456-auth-timeout`, `refactor/ABC-789-cleanup-handlers`.

- **Описание пункта в CHANGELOG**: берётся из части имени ветки **после ключа задачи** (например после `ABC-123`) или из сообщения merge. Имеет смысл давать ветке осмысленный суффикс (например `-add-user-api`), чтобы в CHANGELOG получилось читаемое описание.

**Кратко:** ветки называть `префикс/KEY-NNN-краткое-описание`, мержить в ветку, по которой ставится тег; тогда генератор включит каждый merge в CHANGELOG с нужной категорией и ссылкой на задачу.

---

## 2. Комментарии в коде для документации

- **Где отображаются**: описание **функций** (sections/functions), **gRPC/REST эндпоинтов** (sections/api), **тестов/бенчмарков/примеров** (sections/tests) берётся из комментариев в Go-коде.

- **Формат**: обычные **строчные комментарии `//`** непосредственно **над** объявлением функции/метода/теста. Подряд идущие строки `//` считаются одним комментарием; между комментарием и объявлением допускается не более одной пустой строки.

- **Пример для функции**:

  ```go
  // CreateUser создаёт пользователя по email и имени.
  // Возвращает ID и ошибку при дубликате email.
  func (s *Service) CreateUser(ctx context.Context, req *pb.CreateUserRequest) (*pb.CreateUserResponse, error) {
  ```

- **Пример для теста**:

  ```go
  // TestCreateUser проверяет создание пользователя и обработку дубликата email.
  func TestCreateUser(t *testing.T) {
  ```

- **Не подходят**: комментарии через `/* */` над объявлением (не извлекаются), комментарии далеко от объявления (с большим пустым промежутком), комментарии после объявления.

**Кратко:** писать один или несколько подряд идущих `//` строк прямо над объявлением; без лишних пустых строк между комментарием и объявлением.
